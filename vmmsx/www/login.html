For a **Website User** it prefers, in order: `localStorage.last_visited`, then `?redirect-to`, then the server's answer. The server's answer comes from `get_default_path()`, which on a bench with several apps installed is `/apps` — and Frappe redirects `/apps` to `/desk`, the one address a self-service account cannot open. So the volunteer this whole change is about would sign in successfully and land on a permission error. `last_visited` is the right slot for the fix rather than a convenient one. It is written by exactly one function in the framework — `ask_to_login()`, which stashes the page a signed-out visitor was on before bouncing them here — and read by exactly one, the branch below. Seeding it says the same thing: *this is where you were going*. Nothing else on the site reads it, and `login.js` clears it as it uses it. Two guards, and both matter. It is not written when the URL already carries a `redirect-to`, because `last_visited` would win over it and a person following `RequireAuth` back to a specific screen must get that screen. And it is not written over an existing value, which is a real destination somebody was actually on. **Staff are untouched, and not by accident.** A System User takes the "Logged In" branch, which never looks at `last_visited`; the framework itself makes the distinction, so nothing here has to ask what kind of account is signing in — which is just as well, because at this point nobody knows. -#} {% block script %} {{ super() }} {% endblock %}
