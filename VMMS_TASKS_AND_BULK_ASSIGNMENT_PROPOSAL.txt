VMMS TASKS AND BULK ASSIGNMENT PROPOSAL
=======================================

Bulk tasks should be added. The best design is a bulk-assignment action that
creates separate task records for each selected volunteer, while optionally
grouping them under one batch.

    Bulk task
    +-- Task for Volunteer A
    +-- Task for Volunteer B
    +-- Task for Volunteer C

Each volunteer still gets independent acceptance, progress, evidence,
completion and notification.


CURRENT TASK SYSTEM
===================

For an MVP, the current task system is sufficient. It supports:

* One volunteer per task
* Subject and description
* Optional due date
* Deployment link
* Assignment, acceptance, submission and completion states
* Volunteer questions and coordinator answers
* Progress requests
* Progress updates
* Photo/evidence attachments
* Coordinator sign-off
* Send-back for corrections
* Cancellation
* Notifications
* Volunteer-only ownership checks
* Coordinator geographic scoping
* Full activity history

The model is deliberately simple and has a clear lifecycle.


1. BULK TASK ASSIGNMENT
=======================

The manager should be able to:

* Select several volunteers
* Enter one shared task brief
* Set one due date
* Link the task to a deployment or project
* Preview the selected volunteers
* Create individual tasks
* See which tasks were created successfully
* See volunteers skipped and why
* Notify all selected volunteers

Each generated task should retain:

* The individual volunteer
* A shared batch/group identifier
* The manager who created it
* The common source brief

The bulk operation should validate each volunteer independently. One invalid
volunteer should not prevent valid volunteers from receiving their tasks.


2. PRIORITY AND TASK TYPE
=========================

Add:

* Priority: Low, Normal, High, Urgent
* Task type/category

Why: Managers need to sort attention. A due date alone does not distinguish
routine work from urgent response work.


3. LOCATION AND OPERATIONAL CONTEXT
====================================

The current task has a Geo Node, but that is organisational scope, not
necessarily the actual work location.

Consider adding:

* Physical location/site
* Address or coordinates
* Meeting point
* Local contact
* Travel instructions

Why: A task may be assigned from one branch but performed at another location.


4. ESTIMATED EFFORT AND SCHEDULING
==================================

Add:

* Expected hours
* Planned start date/time
* Planned end date/time
* Actual hours
* Actual completion date

Why: This supports workload balancing, volunteer-hour reporting and stipend
calculations.


5. CHECKLIST AND DELIVERABLES
=============================

The current task has one description field. Add either a checklist child table
or structured deliverables containing:

* Item
* Required/optional
* Completed
* Completed by
* Completed on
* Notes
* Evidence attachment

Why: A long description is difficult to use as an execution checklist. Managers
need to know which parts are complete.


6. ATTACHMENTS AND DOCUMENT REQUIREMENTS
========================================

The current task supports evidence in its update thread. It may also need:

* Briefing documents
* Templates
* Maps
* Forms
* Reference files
* Required completion documents

Why: Operational files should be available before work starts, while evidence
belongs to progress or completion.


7. REASSIGNMENT AND DELEGATION
==============================

Add a controlled reassignment process:

* Reassign to another volunteer
* Reason
* Original volunteer
* New volunteer
* Date/time
* Manager who authorised it

Why: The task is strongly owned by one volunteer. Reassignment should preserve
history instead of editing the volunteer field and losing accountability.


8. ESCALATION AND OVERDUE HANDLING
==================================

Add:

* Overdue status or derived overdue indicator
* Reminder schedule
* Escalation recipient
* Escalation history
* Last contact date
* Response deadline

Why: A manager needs to know not only that a task is open, but that it has gone
unanswered or overdue.


9. DEPENDENCIES AND RELATED TASKS
=================================

Consider:

* Depends on task
* Blocks task
* Parent task
* Related task
* Related deployment/project

Why: Some work cannot begin until another task is complete. This is useful for
deployments and projects.


10. BETTER COMPLETION AND APPROVAL
==================================

The current flow is:

    Volunteer submits -> Coordinator signs off

Add optional completion controls:

* Completion percentage
* Outcome/result
* Manager rating
* Rework required
* Rejection reason
* Final evidence requirement
* Lessons learned

Why: A completed task should record what was achieved, not only that somebody
pressed submit.


11. BULK-TASK REPORTING
=======================

Bulk tasks should have a manager summary showing:

* Total volunteers selected
* Tasks created
* Accepted
* Declined
* Not responded
* In progress
* Submitted
* Completed
* Cancelled
* Overdue

Why: The manager needs a batch-level view while volunteers retain individual
task records.


RECOMMENDED PRIORITY
====================

1. Bulk assignment creating separate individual tasks
2. Bulk-task batch/group tracking
3. Priority and task category
4. Location and scheduling details
5. Checklist/deliverables
6. Reassignment history
7. Overdue reminders and escalation
8. Completion outcomes and reporting
9. Dependencies and related tasks


FINAL ASSESSMENT
================

The current task system is sufficient as a controlled one-volunteer work item.
The main immediate limitation is not its lifecycle; it is the lack of bulk
assignment and management-level reporting around multiple related tasks.

Bulk assignment should create separate linked tasks rather than immediately
turning one task into a shared multi-volunteer record. This preserves individual
accountability, acceptance, progress, evidence and completion while giving the
manager the convenience of selecting many volunteers at once.
