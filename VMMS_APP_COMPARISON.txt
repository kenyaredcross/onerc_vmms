VMMS CURRENT APP VS VMMS1 REFERENCE APP
========================================

Scope
-----

This document compares the current vmmsx repository with the supplied merged
metadata from vmms1.localhost. Layout-only fields are excluded. The comparison
distinguishes genuinely missing capabilities from functions that exist under a
different DocType or domain model.

Summary
-------

The current app is substantially richer in volunteer lifecycle management,
approvals, deployment management, certifications, and geographic control. The
clearest missing areas are financial/ERP integration, full project accounting,
strict Terms of Reference completeness, TOR document attachments, and a genuine
volunteer-opportunity workflow.

Area                         Assessment
---------------------------  -------------------------------------------------
Volunteer registration       Current app is richer; some ERP links are absent
Membership registration      Operationally richer; financial integration is incomplete
Projects                     VMMS Project is much lighter than ERPNext Project
Terms of Reference           Similar structure; current completeness rules are weaker
Deployment                   Richer architecture; several fields/attachments are absent
Events                       Uses Buzz instead of ERPNext Event; not a direct field gap
Opportunities                Uses HRMS Job Opening; lacks volunteer interest workflow


1. VOLUNTEER REGISTRATION
=========================

The reference app's VM Member is only a basic person/ERP linkage record. The
current app separates this into:

* Red Profile - personal identity and contact information
* VMMS Volunteer Application - registration and approval
* VMMS Volunteer - approved operational record
* VMMS Member - membership identity
* VMMS Membership - individual membership terms

This is a better separation than the reference structure.

The current volunteer application adds capabilities absent from the reference:

* Serving branch
* Skills
* Languages
* Availability
* Motivation
* Prior experience
* Custom questions and attachments
* Approval stages and decisions
* Draft, submission, review, approval, rejection and withdrawal states

The resulting volunteer also has an Employee link.

Missing relative to VM Member
-----------------------------

* Customer link
* Supplier link
* Customer name
* A direct User/email link on the volunteer/member record

These may not be genuine requirements. Identity and email belong to Red
Profile, while Employee is already connected to VMMS Volunteer. Customer and
Supplier links are valuable only if volunteers or members participate directly
in ERPNext sales, billing, reimbursements or procurement.

Image
-----

The reference has a hidden image attachment. The current app instead stores the
person's profile photograph on Red Profile, so this is not missing functionally.

Registration attachments
------------------------

The current system supports configurable attachment questions through VMMS
Application Question and VMMS Application Answer. This is more flexible than
the reference metadata, which shows no registration attachment.

However, no fixed ID-document attachment is required by the core volunteer
form. If the operational requirement is "every volunteer must upload an ID
copy," that policy is missing unless configured as a required attachment
question.


2. MEMBERSHIP REGISTRATION
==========================

The current membership has:

* Member and membership type
* Geographic branch/node
* Automated status
* Renewal chain
* Validity dates
* Payment transaction and receipt references
* Payment confirmation time
* Proof-of-payment attachment
* Configurable questions
* Approval workflow
* Card token
* Fee, currency, duration and certificate template on VMMS Membership Type

Missing or represented differently
----------------------------------

* Company is missing. The current app uses Geo Node, which handles operational
  ownership but not accounting-company ownership.
* Amount is not stored as a transaction snapshot on each membership. It lives
  on Membership Type. If the fee changes, the membership may not preserve the
  amount originally charged.
* Currency has the same issue: it is defined on Membership Type rather than
  snapshotted on the membership.
* A Paid checkbox is not necessary because paid_on, payment transaction and
  lifecycle status provide stronger evidence.
* Member-since date is not stored on each membership. VMMS Member.joined_on and
  the earliest active membership can represent it.
* A QR image is not stored as an uploaded image. The system uses card_token and
  generated card/certificate functionality.
* Payment is stored as Data references, not strong Links to Payment Entry,
  Sales Invoice, Payment Request or another accounting DocType.

Important financial gap
-----------------------

The major missing feature is an auditable ERPNext accounting relationship:

* Company
* Charged amount and currency snapshot
* Payment Entry or Sales Invoice
* Reversal/refund handling
* Payment status derived from accounting records

This matters if membership fees must reconcile with finance.


3. PROJECT CREATION
===================

This is the largest direct gap.

The current VMMS Project contains only:

* Series
* Project name
* Status
* Geo node
* Start and end dates
* Summary
* Notes

Missing compared with ERPNext Project
-------------------------------------

* Project type
* Priority
* Department
* Company
* Customer
* Sales order
* Project template
* Project users and their permissions
* Percentage-complete method
* Percentage completed
* Task-based progress calculation
* Active flag distinct from lifecycle status
* Timesheet integration
* Actual start/end dates
* Actual hours
* Estimated costing
* Timesheet costing
* Expense claim totals
* Purchase cost
* Material consumption cost
* Sales and billing totals
* Gross margin and gross-margin percentage
* Cost center
* Holiday list
* Automated progress collection and reminder schedule
* Progress email subject/message
* Unique project-name enforcement

This appears intentional: VMMS Project is a lightweight operational programme
container, not an ERP project.

If projects must control budgets, purchases, expenses, donor reporting or staff
time, this is the highest-priority functional gap.


4. PERSONNEL TERMS OF REFERENCE
===============================

The current TOR is structurally close to the reference and adds:

* Stable immutable key
* Active/retired control
* Optional standing TOR without a project
* Default duration
* Geographic scope
* Purpose
* Required certifications
* Responsibilities
* Direct or routed approval
* Amendments
* Submittable document semantics

Missing fields or weaker definitions
------------------------------------

* Region/company: the current app uses optional geo_scope, not a required
  Company.
* Required project: Project is intentionally optional for standing duties.
* Mandatory dates: start and end are optional.
* Mandatory mission background: present, but not required.
* Mandatory child sections: stakeholders, objectives, outputs, approaches,
  itinerary and resources exist but are not declared required.
* Approach notes: present but not required.
* Itinerary time: present but not required.
* Person responsible: present but not required.
* Resource date: present as optional needed_on.
* Resource donor: plain Data rather than Link to a donor register.
* Resource project: missing from each resource line.
* Resource unit: plain Data rather than Link to UOM.
* Resource quantity: not required and has no declared default of 1.
* Resource unit cost: not required.

The most important difference is completeness enforcement. The reference
refuses incomplete TORs at metadata level, while the current app permits
lightweight or partially specified TORs.

Some flexibility is intentional, but submission could enforce different rules
for:

* Standing reusable TOR templates
* Fully planned mission TORs
* Emergency deployments where details may initially be incomplete


5. DEPLOYMENT
=============

The reference combines one person's deployment request into a single Personnel
Deployment Request. The current app separates the domain into:

* VMMS Deployment Request - organisational request and approval
* VMMS Deployment - actual operation
* VMMS Deployment Assignment - one volunteer's invitation/placement and answer
* VMMS Task - work assigned to a volunteer
* VMMS Deployment Update - operational updates
* VMMS Branch Transfer - movement between branches

The assignment record supports invitation, acceptance/decline, role, planned
period, actual joining/leaving and participation notes.

Missing relative to the reference
---------------------------------

* Direct Employee field on an assignment
* Direct User field
* Project copied directly onto the assignment
* Task link directly on the assignment
* Specific deployment Location link
* TOR file attachment
* TOR URL
* A general rich-text deployment note
* Explicit Rejected status; the current equivalent is Declined
* Expected dates as Datetime; current assignment dates are Date fields
* Expected end date requirement matching the reference

Most Employee/User/Project values can be resolved through Volunteer -> Red
Profile/Employee and Deployment -> TOR -> Project. They are not necessarily
missing functionally, but direct snapshot fields could improve historical
reporting.

Important real gaps
-------------------

* Specific worksite/location: Geo Node identifies organisational/geographic
  scope, but is not necessarily a physical deployment location.
* TOR attachment or immutable rendered snapshot: assignments point to the exact
  TOR record, but there is no attached signed/exported version.
* Time precision: deployment and assignment dates are dates, not datetimes.


6. EVENTS
=========

This is not a direct comparison because the current app intentionally uses
Buzz Event, not ERPNext's standard Event.

The current app adds:

* Geographic event placement
* Published public-event browsing
* Event detail pages
* Volunteer/member attendance
* Attendance cancellation
* Portal calendar integration

The reference Event offers generic calendar capabilities that may or may not
exist in Buzz:

* Private events
* Recurrence
* Google Calendar synchronization
* Google Meet creation
* Arbitrary Dynamic Link references
* Participant invitations
* Reminder rules
* Email/notification schedules

These are potential integration gaps, not proven missing event capabilities.
The current app has chosen a public/community event system, while the reference
uses a general-purpose internal calendar.

A likely missing operational distinction is between:

* Public Society events
* Internal meetings
* Calls and correspondence
* Recurring administrative calendar events


7. OPPORTUNITIES
================

The current app already reads HRMS Job Opening, the same DocType listed in the
reference. Therefore, the listed Job Opening fields are not missing when HRMS
is installed.

The portal provides published-opening browsing and detail pages. The more
significant issue is conceptual: HRMS Job Opening represents employment
recruitment, not necessarily volunteer work.

Missing volunteer-opportunity capabilities
------------------------------------------

* A VMMS-owned Volunteer Opportunity DocType
* Opportunity type: event, deployment, task, recurring role or general service
* Skills/certifications required
* Number of volunteers needed
* Geographic eligibility
* Availability period
* Volunteer expression of interest
* Application questions
* Interest status and review
* Selection or rejection
* Conversion into deployment assignment, event role or task
* Withdrawal by the volunteer
* Opportunity-specific communication history

This is a larger functional gap than any missing Job Opening field.


RECOMMENDED PRIORITIES
======================

1. Create a financial audit trail for memberships: company, amount/currency
   snapshot and accounting-document links.
2. Decide whether projects require ERP accounting. If they do, link VMMS
   Project to ERPNext Project instead of duplicating all its costing fields.
3. Strengthen TOR submission validation, especially objectives, outputs,
   methodology, itinerary and resources.
4. Strengthen TOR resources with Donor and UOM links, required quantity/cost and
   optional funding/project allocation.
5. Add a physical deployment location and immutable TOR attachment/snapshot.
6. Introduce a genuine Volunteer Opportunity and Interest workflow, while
   keeping HRMS Job Opening for employment.
7. Configure required registration documents by jurisdiction, such as ID copy,
   consent, guardian approval, professional certificate or referral letter.


FINAL ASSESSMENT
================

The reference app is not categorically more complete; it is more ERP-centric.
The current app is more complete as a volunteer-management system, but it stops
short where volunteer operations meet accounting, project costing, formal
document control and opportunity applications.
