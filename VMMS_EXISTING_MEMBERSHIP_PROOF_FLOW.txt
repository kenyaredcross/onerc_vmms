EXISTING MEMBERSHIP PROOF FLOW
=============================

Goal
----

Allow a person with an account to prove that they already belong to a selected
membership plan, so the society can verify the evidence and create/activate a
membership record without requesting a new gateway payment.


Existing membership plan page
=============================

When a person opens the Membership tab:

1. Show the available membership plans.
2. Let the person select a plan.
3. Show the plan name, description, fee, duration, lifetime status and benefits.
4. Show two actions at the bottom:

   * Apply for this membership
   * Already a member of this plan?

The second action should be visually secondary so a new applicant is not
confused with somebody proving an existing membership.


Existing-member proof form
==========================

When the person clicks "Already a member of this plan?", open a short form.

Person
------

Automatically fill the following from the account/profile:

* Full name
* Email
* Phone
* Account/profile
* Existing VMMS Member record, if one exists

These fields should be read-only. The applicant should not retype their identity.

Membership plan
---------------

Carry the selected plan into the form automatically:

* Membership type
* Plan name
* Plan duration
* Lifetime/permanent status
* Fee and currency for reference

The user should not change the plan inside the proof form unless they return to
the plan list.

Historical membership details
-----------------------------

Ask for:

* Date originally registered or joined
* Membership number, if available
* Branch or location where they registered
* Previous certificate number or receipt number, optionally

Label dates carefully. Date registered may not be the same as date paid or date
the membership became active.

Prefer these concepts where the data model supports them:

* Original registration date
* Effective membership start date
* Payment/receipt date, optional

Expiry
------

For non-lifetime plans:

* Show an expiry-date field.
* Make it required.
* Validate that it is after the registration/start date.

For lifetime plans:

* Hide the expiry field.
* Store expiry as empty/null.
* Display "Lifetime" rather than a placeholder date.

The existing membership type model already supports this using `is_lifetime`.
`duration_days` is used for non-lifetime memberships.

Proof document
-------------

Require one private attachment labelled:

    Upload proof of existing membership

Accepted evidence could include:

* Receipt
* Membership certificate
* Membership card
* Other approved evidence

The file should be private and visible only to the applicant and authorised
approvers.

Declaration
----------

Add a required confirmation such as:

    I confirm that the information provided is accurate and that this document
    belongs to me.

Record the submission date and, ideally, the version of the declaration text
accepted.


Workflow
========

    Select plan
        -> Already a member
        -> Confirm identity
        -> Enter historical dates
        -> Upload proof
        -> Submit
        -> Approval
        -> Membership activated

The record should enter `Awaiting Approval` and should not create a new payment
gateway transaction.

After approval:

* Membership becomes Active.
* `valid_from` uses the verified historical start date, if policy allows
  backdating.
* `valid_to` uses the verified expiry date for a non-lifetime plan.
* A lifetime membership has no `valid_to`.
* The proof remains attached to the membership record.


Backdating decision
===================

Decide whether approval uses the applicant's submitted date or a date verified
by the approver.

Recommended approach:

* Applicant submits claimed start and expiry dates.
* Approver can correct them.
* Store claimed and verified dates separately.
* Membership validity uses the verified dates.

This prevents an unverified historical date from becoming the official date.


Fit with current implementation
===============================

The current backend already supports most approval mechanics:

* `membership_source = Proof`
* `proof_attachment`
* Routed approval
* No gateway payment
* Approver access to the attachment
* Activation after approval
* Lifetime membership handling

What is missing for this proposed user experience is primarily:

* Member-facing entry point from the selected plan
* Self-service proof form
* Passing the selected plan into that form
* Historical start and expiry fields
* A member-facing submission endpoint for this request
* Clear distinction between ordinary new membership and proof of existing
  membership
* Potentially separate claimed and verified dates


Recommended domain distinction
==============================

Keep the two journeys distinct even if both eventually create a VMMS Membership:

New applicant
------------

    I want to become a member.

Existing member
--------------

    I already belong to this plan; please verify my evidence and record me.

This distinction will make the portal easier to understand and the approval
queue much clearer.
