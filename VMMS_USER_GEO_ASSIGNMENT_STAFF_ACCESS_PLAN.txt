VMMS USER, GEO ASSIGNMENT AND STAFF ACCESS PLAN
================================================

Objective
---------

Make staff setup easier by allowing administrators to configure a user's role
profile and default Geo Node from the User form, while ensuring Desk access is
still restricted to the records that user is authorised to see.

The central design rule is:

    The User form is the setup interface.
    Geo Assignment remains the security and audit source of truth.


1. USER FORM
============

Add or expose these staff-access fields on the User form:

* Role Profile
* Default Geo Node
* Optional access-expiry date

Also show an Access Assignments section on the User page containing linked
Geo Assignment records:

* Role
* Geo Node
* Start date
* End date
* Source
* Active/inactive status
* Reason

The records should remain separate Geo Assignment documents. The User form is
simply the convenient place to view and manage them.


2. WHY GEO ASSIGNMENT REMAINS SEPARATE
======================================

Do not store a second copy of the security data in a User child table.

If User and Geo Assignment each store the same access information, they can
diverge:

* User shows access that Geo Assignment does not grant.
* Geo Assignment grants access that User does not show.
* Manual assignments are overwritten by synchronization.
* Expiry dates differ.
* Duplicate detection becomes harder.

The permission engine already reads Geo Assignment, so it must remain the single
source of truth.


3. ROLE PROFILE AND DEFAULT GEO NODE
====================================

When an administrator selects a Role Profile and Default Geo Node, the system
should preview the assignments that will be generated.

Example input:

    Role Profile: County Operations Staff
    Default Geo Node: Nairobi County

Generated access:

    Volunteer Coordinator | Nairobi County
    Membership Officer   | Nairobi County
    Task Coordinator     | Nairobi County

The administrator should see the preview before confirming the change.


4. STAFF ACCESS AUTHORITY
=========================

Only System Managers or specifically authorised administrators should edit
staff access.

A separate approval workflow is not required because the editor is already the
designated authority. Auditability remains required.

Do not grant System Manager broadly. Where branch administrators need to manage
staff, create a narrower administrative role instead.


5. SYNCHRONISATION RULES
========================

When the User's role profile or default node changes:

* Add assignments for newly selected roles.
* Keep existing assignments that are still valid.
* Do not create duplicates.
* Mark removed role-profile assignments inactive or end-date them.
* Preserve manually created assignments.
* Do not delete historical records.
* Record whether each assignment came from a Role Profile or was created
  manually.
* Require a reason for escalation or removal.

The administrator should see a change summary before saving:

    Assignments to add: 1
    Assignments to end: 2
    Manual assignments preserved: 1


6. ROLE PROFILE DELETION
========================

Do not physically delete all assignments when a Role Profile is deleted.

Recommended behaviour:

* End-date or deactivate assignments generated by that profile.
* Preserve the audit record.
* Leave manually created assignments untouched.
* Log the profile deletion and resulting access changes.
* Warn the administrator if active users will lose access.

If automatic removal is required, only remove assignments explicitly marked as
managed by that profile, for example:

    managed_by_role_profile = 1
    source_role_profile = County Operations Staff

Never remove manually created assignments automatically.


7. DUPLICATE PREVENTION
=======================

Prevent duplicate active assignments using:

    User + Role + Geo Node

If validity dates are supported, also prevent overlapping active periods for the
same combination.

Duplicate prevention should exist at two levels:

* Application validation, for a clear user-facing message.
* Database-level uniqueness where possible, to prevent race-condition duplicates.

Expired historical assignments should normally remain in place. A new assignment
may be created later for a new period.


8. ESCALATION
=============

Do not change the user's default Geo Node for a temporary escalation. Add a
separate, time-limited Geo Assignment.

Example:

    Normal:
    Amina | Volunteer Coordinator | Nairobi County

    Temporary escalation:
    Amina | Volunteer Coordinator | National Office
    Valid until: 15 September
    Reason: National registration review

When the assignment expires, the broader access disappears automatically.


9. STAFF SETUP FLOW
===================

The desired setup flow is:

    Create User
        -> Select Role Profile
        -> Select Default Geo Node
        -> Preview generated access
        -> Confirm
        -> Create/update Geo Assignments
        -> Verify inside/outside-node access

The verification step should test:

* A record inside the assigned node
* A record beneath the assigned node
* A record outside the assigned node
* A document from another module
* A document after the assignment expires

The outside-node record should not appear in list views, searches, reports or
API responses.


10. ACCESS MODEL TO PRESERVE
============================

Keep the following architecture:

* Geo Assignment determines where authority applies.
* Role determines what the user can do.
* DocType permissions determine whether the role may read, create or write.
* Geo scoping filters records to the assigned node and descendants.
* Volunteers use portal ownership access and do not need Desk permissions.
* System Managers remain unrestricted and should be assigned sparingly.

The effective permission is:

    User + Role + Geo Assignment + DocType permission


11. VOLUNTEER APPLICATION EXCEPTION
====================================

Review the current exception for VMMS Volunteer Application. The application is
deliberately not geo-scoped and some staff read it nationally.

Choose one policy:

* Branch-restricted applications: staff see applications in their node.
* Approver-restricted applications: staff see applications routed to them.
* Central review: a national role sees all applications, branch staff see only
  approved volunteer records.

Recommended policy:

* Branch staff see applications for their assigned branch.
* Approvers see applications routed to them.
* A central volunteer administrator can see all applications.
* Sensitive attachments have tighter access than basic application details.


FINAL RECOMMENDATION
====================

Use this structure:

    User
    +-- Role Profile
    +-- Default Geo Node
    +-- Linked Geo Assignment records

The User form becomes the staff-access control panel, but Geo Assignment remains
the authoritative permission, scope and audit record.

This provides one-screen staff administration without weakening geographic
access control, escalation handling, expiry, duplicate prevention or auditability.
